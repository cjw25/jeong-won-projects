# 계획 설계서 — 안심 한 걸음

- 상태: 자동화 중심 웹 MVP 초안
- 작업명: 안심 한 걸음 (확정 전)
- 현재 형태: 모바일 우선 반응형 웹 프로토타입

## 1. 목표

보안 지식이 많지 않은 사람도 반복적인 위험 신호 확인을 자동으로 도움받고, 문제가 생겼을 때 안전한 다음 행동을 쉽게 찾게 한다. 자동화의 범위와 한계를 분명히 알리고, 앱이 모든 위협을 탐지하거나 완벽한 보호를 제공한다고 오해시키지 않는다.

## 2. 대상 사용자와 설계 원칙

- 스마트폰·온라인 계정의 보안 설정이 낯선 일반 사용자
- 큰 글씨, 명확한 버튼, 쉬운 한국어, 키보드 및 화면 읽기 지원을 고려한다.
- 공포를 조장하거나 사용자를 탓하지 않고, 한 번에 실행할 수 있는 행동을 안내한다.
- 자동 분석은 가능한 한 기기 안에서 처리하고, 주소·메시지·계정정보를 서버로 보내지 않는다.
- 자동 판정이 불완전할 수 있음을 결과와 함께 설명한다.

## 3. 현재 MVP 범위

1. **페이지 환경 자동 점검**: 페이지가 HTTPS, HTTP, 로컬 파일 중 어떤 방식으로 열렸는지 확인한다. 브라우저 저장 공간을 임시 키로 시험하고 바로 지운다. 현재 화면에서 확인할 수 있는 외부 리소스 호스트를 표시한다. 점검은 페이지를 열 때 실행하고 다시 실행할 수도 있다.
2. **링크 형식 자동 분석**: 사용자가 공유해도 괜찮다고 판단한 웹 주소를 브라우저 안에서 분석한다. HTTP 사용, 주소 내 사용자 정보, IP 주소, 일부 알려진 단축 주소, punycode 도메인 등 단순 신호를 표시한다. 링크를 열거나 네트워크 평판 조회를 하지 않으며, 입력값을 저장하지 않는다.
3. **기본 보안 안내**: 화면 잠금, 업데이트, 주요 계정 보호, 복구 정보를 사용자가 직접 확인한다. 완료 표시는 현재 브라우저의 로컬 저장소에 보관한다.
4. **사고 대응 안내**: 계정 정보 노출, 금융 피해, 링크·파일 실행, 계정 접근 불가에 대한 일반적인 다음 행동을 제공한다.

## 4. 자동화의 한계와 제외 범위

현재 웹앱은 브라우저의 보안 경계 때문에 운영체제 설정, 설치 앱, 악성 파일, SMS, 다른 앱의 링크 클릭, 계정 로그인 상태를 읽거나 바꿀 수 없다. 기기 전체를 백그라운드 감시하거나 악성코드를 탐지·차단하지 않는다.

링크 자동 분석은 제한된 문자열 규칙일 뿐이다. 알려지지 않은 공격을 놓칠 수 있고 정상 링크에 주의 표시를 할 수도 있다. 신호가 없다고 링크가 안전하다는 뜻은 아니다. HTTPS도 사이트의 신뢰성을 보장하지 않는다. 전체 메시지·비밀번호·인증번호·금융 정보는 입력받지 않는다.

## 5. 실제 기기 보안 자동화를 위한 다음 결정

- 사용자와 실제 보안 기능을 확인한 뒤 첫 네이티브 대상(Android/iOS 등)을 정한다.
- 선택한 플랫폼이 허용하는 공식 API만 사용하고, 권한·백그라운드 실행·앱 심사 정책을 검토한다. 네이티브 앱도 다른 앱이나 운영체제의 모든 상태를 마음대로 검사할 수 있는 것은 아니다.
- 평판 조회를 추가할 경우 링크가 외부 사업자에게 전송될 수 있으므로, 전송 데이터 최소화·사용자 동의·보관 기간·오탐 대응을 먼저 설계한다.
- 위협 모델, 개인정보 영향, 접근성, 오탐·누락 시 사용자 안내를 검토한 뒤 구현한다.

## 6. 완료 기준

- 페이지 환경 점검이 시작 시 자동 실행되고, 재실행 버튼으로 갱신된다.
- 페이지 연결 방식, 임시 저장 시험, 확인 가능한 외부 리소스 결과가 각각 구분되어 표시된다.
- 주소 입력은 브라우저 안의 규칙 검사만 수행하며 주소를 열거나 네트워크로 보내거나 저장하지 않는다.
- 링크 결과가 위험을 확정하거나 안전을 보장하지 않는다는 설명이 보인다.
- 화면 잠금·기기 업데이트 등 브라우저가 읽을 수 없는 설정은 자동 점검 결과인 것처럼 표시하지 않는다.
- 모바일 화면, 키보드 조작, 상태 안내 및 개인정보 안내를 확인한다.

## 7. 진행 순서

1. 웹 MVP에서 가능한 투명한 자동 점검과 로컬 링크 신호 분석을 구현한다.
2. 직접 브라우저 실행과 키보드·작은 화면 검토를 하고, 사용자가 자동 결과를 과신하지 않는지 확인한다.
3. 사용자가 원하는 실제 자동 보호 기능과 대상 플랫폼을 정한다.
4. 플랫폼별 권한·정책·개인정보·보안 검토를 마친 후 네이티브 기능을 설계한다.
